# Landing-Page-Relevant Product UX Review

## Scope

This review exists only to help communicate the product accurately and design a trustworthy landing page. It is not an application redesign brief.

## Findings that affect the landing page

### The current workflow is not obvious from navigation alone

Discovery, Calendar, Generator, Audit, and Rank Tracker appear as separate destinations. A visitor shown isolated screens could interpret the product as a bundle of unrelated tools.

**Landing-page implication:** demonstrate one item moving through `Discover -> Prioritize -> Plan -> Create -> Measure -> Improve`. Shared context should remain visible throughout.

### “Scheduled” can imply CMS publishing

The screenshots prove editorial scheduling but do not prove direct CMS publishing. The public FAQ describes CMS integrations as planned.

**Landing-page implication:** use “planned,” “placed on the calendar,” or “ready to create” unless direct publishing is confirmed. Answer the CMS question plainly in the FAQ.

### Persistent project context is an important differentiator

Project memory, covered topics, the project brief, sitemap context, and research inputs support a stronger story than generic prompt-based generation.

**Landing-page implication:** show the system carrying audience, brand, topic, and performance context between stages. Do not leave this concept buried in a feature list.

### The product should read as a loop

Keyword evidence leads into planning and creation; audits and rank tracking can inform the next improvement. The screenshots show the components, but not a single continuous artifact history.

**Landing-page implication:** the marketing demonstration may compose multiple truthful product states into one narrative, as long as it does not imply a current interaction or automation that does not exist.

### Breadth can weaken the story

Blogs, ebooks, whitepapers, LinkedIn posts, audits, internal links, and rank tracking demonstrate depth. Presented equally, they can make the page feel like an AI utility bundle.

**Landing-page implication:** anchor the story on the organic-growth loop. Treat formats and helper features as depth within that system.

### Current and future automation need visible boundaries

Current screens show AI-assisted research and generation with user actions. Agent Mode is not implemented. Fully autonomous operation and publishing are not demonstrated.

**Landing-page implication:** label capability states consistently:

- **Available today:** connected workflow, keyword evidence, calendar, assisted briefs and content, audits, rank tracking, persistent context.
- **Partially automated:** AI keyword ideas, brief completion, researched generation, content analysis.
- **Coming Soon:** Agent Mode is intended to increasingly automate the workflow; detailed behavior is not yet finalized.
- **Planned or unverified:** autonomous CMS publishing and unrestricted end-to-end operation.

### Product proof must avoid misleading states

The research screenshots contain empty states, private project details, a missing sitemap, and a worker warning. They were supplied only to explain the product.

**Landing-page implication:** create purpose-built product states later. They should be truthful, coherent, and designed around the story being told.

## Deferred future-product notes

The following observations may matter to the product team but are explicitly outside this landing-page assignment:

- A canonical in-app lifecycle and state model.
- Content-library naming and status architecture.
- Search Console connection ownership.
- AI Score naming or explanation.
- Asset-level performance views.
- Setup and onboarding systems.
- Detailed regeneration and any future Agent Mode interaction architecture.
